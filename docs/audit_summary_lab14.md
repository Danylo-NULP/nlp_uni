# Audit Summary - Lab 14

## 1. Use Case
Оркестрована обробка та класифікація описів фотографій (Image Captions SNLI).
Система приймає сирий текст, очищає його, маршрутизує (Люди, Тварини, Пейзажі), застосовує специфічну схему екстракції, перевіряє на галюцинації та безпечно експортує у структурованому форматі.

## 2. Які етапи flow реалізовано
Пайплайн побудовано як керований stateful workflow:
1. **Ingest** — приймання тексту, генерація case_id, очищення шуму, перевірка на порожній ввід.
2. **Route** — визначення фокусу зображення для обрання цільової схеми (human_focus, animal_focus, scenery_focus, unknown).
3. **Execute** — локальна LLM (Llama-3) витягує дані за жорсткою JSON-схемою.
4. **Validate** — перевірка відповідності виводу схемі (через `jsonschema`) та відловлювання пустих обов'язкових полів.
5. **Fallback** — обробка відхилень (маркування кейсу як Needs Manual Review, якщо валідація провалена).
6. **Export** — формування стабільного JSON-експорту, незалежно від того, як завершився процес (успіх чи безпечний збій).

## 3. Скільки test cases
Всього 10 тестових кейсів, які покривають успішні шляхи, порожні дані, помилки схеми (масив замість рядка), та фатальні збої (симуляція ін'єкцій).

## 4. Метрики роботи пайплайну
* **Flow completion rate:** ~70% (завершили експорт з даними або частковими даними).
* **Validation pass rate:** Залежить від виводів локальної моделі, зазвичай 40-50% без жодних проблем.
* **Fallback activation rate:** Спрацьовує на текстах типу "A person." або при помилках типізації LLM.
* **Export valid rate:** Відображає, скільки кейсів повернули валідний об'єкт JSON.

## 5. Найкращі приклади flow
* **tc_001 ("A man in a blue shirt..."):** Ідеальний шлях. Роутер чітко визначив категорію (human), екстрактор заповнив поля, валідатор підтвердив схему, експорт пройшов ідеально.
* **tc_008 (Зашумлений текст):** Успішна обробка тексту з купою знаків оклику. Етап Ingest очистив шум, і Flow відпрацював без перешкод.
* **tc_006 ("A wooden table."):** Показовий приклад Safe Failure. Текст занадто бідний. Валідатор зафіксував недостачу дій чи атрибутів, запустив fallback, і система маркувала запис як *Needs Manual Review*, зберігши часткові дані.

## 6. Проблемні приклади
* **tc_003 ("How to cook pizza?"):** Запит на нецільову тему. Роутер присвоїв статус `unknown`, через що етап виконання був пропущений, і Flow безпечно завершився без падіння системи.
* **tc_007 ("DROP TABLE users"):** Симуляція критичного збою під час виконання (`execution_error`). Fallback спрацював, але даних не відновив. Експорт повернув стабільний JSON з логом помилки.

## 7. Що flow покращив порівняно з ad-hoc pipeline (Multi-Agent)
* **Контроль Стану (State):** Тепер між кроками передається лише об'єкт `FlowState`. Код став чистим, без глобальних змінних.
* **Локалізація Помилок:** Будь-яка помилка не вбиває скрипт. Вона записується у `state.errors`, і наступні кроки самі вирішують, чи працювати далі.
* **Стабільність Експорту:** Зовнішні бази даних гарантовано отримають об'єкт від кроку `Export`, навіть якщо всередині LLM згалюцинувала чи видала фатальну помилку.

## 8. Що б ви покращували далі
1. **Self-Correction (Retry Loop):** Наразі Fallback лише фіксує збій. Можна додати міні-цикл: якщо Validate каже "Це не масив", відправити текст назад в Execute з промптом "Виправ на масив".
2. **Паралельна екстракція:** Для складних фото (наприклад, пейзаж + люди) дозволити Роутеру обирати кілька схем одночасно і запускати Execute у кілька потоків.
